## 1. เป้าหมาย

แอปเดียว รองรับผู้ใช้ 3 บทบาท ทำงานครบโดยไม่ต้องเปิดเว็บ และขึ้น App Store / Play Store ได้จริง

| บทบาท | ใช้แอปทำอะไร |
|---|---|
| **พนักงาน** | ลงเวลา GPS · ยื่นลา/OT/แก้เวลา/นอกสถานที่ · ดูสลิป + 50 ทวิ · ปฏิทินงาน+วันหยุด · โปรไฟล์ · แจ้งเตือน |
| **หัวหน้า** | ทุกอย่างของพนักงาน + อนุมัติใบคำขอ · dashboard ทีม (วันนี้ใครมา/สาย/ลา) |
| **ผู้บริหาร** | ทุกอย่างของพนักงาน + ภาพรวมบริษัท (กำลังคน ค่าจ้าง OT แนวโน้ม) |

**นิยาม "เสร็จ"**: พนักงาน TJC ทั้ง 18 คนติดตั้งจากสโตร์ ล็อกอิน ใช้งานได้จริงครบหนึ่งงวดเงินเดือน โดยไม่มี crash และไม่ต้องมีใครเปิดเว็บช่วย

## 2. หลักการตัดสินใจ (ADR)

### ADR-001 — Backend เดิมตัวเดียว ห้ามแยก (คงเดิม)
แอปเรียก NestJS ตัวเดียวกับเว็บ ตัวเลขทุกจอต้องมาจากแหล่งเดียวกับที่ HR เห็น
เพิ่มได้เฉพาะ endpoint ใน `MobileModule` ที่เป็น aggregate เพื่อลดจำนวน round-trip

### ADR-002 — "รื้อ" หมายถึงรื้อชั้น UI/UX ไม่รื้อชั้นความปลอดภัย
ของที่ผ่านการตรวจความปลอดภัยและใช้งานจริงแล้ว **เก็บไว้**:
- ระบบล็อกอิน + refresh token + ผูกเครื่อง (device binding) + จอ 2FA
- `bootstrap` / `today` orchestrator ฝั่ง backend
- การลงเวลา GPS + geofence + idempotency key

ของที่ **รื้อเขียนใหม่ทั้งหมด**:
- Design system (สี ตัวอักษร ระยะ คอมโพเนนต์) — ยกชุดใหม่ให้ตรงกับ design เว็บ (sky/cyan)
- โครง navigation ทั้งหมด — เดิมเป็น 5 แท็บตายตัว เปลี่ยนเป็นแท็บตามบทบาท
- ทุกหน้าจอที่มีอยู่ (today / attendance / requests / profile / wallet)
- ชั้นจัดการ error + empty + loading ให้เป็นระบบเดียวทั้งแอป

เหตุผล: เขียน auth ใหม่ = เปิดความเสี่ยงที่ปิดไปแล้วกลับมาใหม่ โดยไม่ได้คุณค่าอะไรเพิ่ม

### ADR-003 — ทุกฟีเจอร์เปิด/ปิดด้วย Feature Flag จาก backend
`mobile-feature-flag.service` มีอยู่แล้ว — แอปห้าม hardcode ว่าใครเห็นอะไร
ต้องอ่านจาก flags + permissions ที่มากับ bootstrap เสมอ (เพิ่ม flag ใหม่: `approvals`, `executive`)

### ADR-004 — Offline อ่านได้เสมอ เขียนได้เฉพาะลงเวลา
- อ่าน: cache ด้วย TanStack Query + persist ลง SQLite (มีโครง `lib/database` แล้ว)
- เขียน: คิว offline เฉพาะ "ลงเวลา" (สำคัญสุด เน็ตหน้างานไม่แน่นอน) — ใบลา/OT ต้องออนไลน์
  เพราะมี validation ฝั่ง server เยอะ (โควตา วันซ้อน งวดล็อก) ที่ทำ offline แล้วจะโกหกผู้ใช้

## 3. Stack (ยืนยันของเดิม เพิ่มบางตัว)

| ชั้น | ใช้ | หมายเหตุ |
|---|---|---|
| Framework | Expo SDK 57 + expo-router | มีแล้ว |
| ภาษา | TypeScript strict | มีแล้ว |
| Server state | TanStack Query 5 | มีแล้ว |
| Client state | zustand | มีแล้ว |
| Secure storage | expo-secure-store | มีแล้ว (token) |
| Local DB | expo-sqlite | มีโครงแล้ว (คิว offline + cache) |
| Push | expo-notifications + Expo Push Service | **เพิ่มใหม่** (schema มี `expoPushToken` รอแล้ว) |
| Crash/Error | Sentry (sentry-expo) | **เพิ่มใหม่** |
| E2E | Maestro | **เพิ่มใหม่** (เขียน flow เป็น YAML ง่ายสุดสำหรับ RN) |
| Build/Deploy | EAS Build + EAS Submit + EAS Update | มี eas.json แล้ว ต้องเติม profile |

## 4. โครงหน้าจอทั้งหมด (Information Architecture)

### แท็บตามบทบาท (จาก feature flags)

```
พนักงาน   [หน้าหลัก] [ลงเวลา] [คำขอ] [เงินเดือน] [ฉัน]
หัวหน้า    [หน้าหลัก] [ลงเวลา] [คำขอ] [อนุมัติ●] [ฉัน]     ● = badge จำนวนรออนุมัติ
ผู้บริหาร  [หน้าหลัก] [ภาพรวม] [คำขอ] [เงินเดือน] [ฉัน]
```
หัวหน้าเข้าหน้าเงินเดือนตัวเองได้จากแท็บ [ฉัน] · ผู้บริหารที่มีลูกทีมเห็นอนุมัติในหน้าหลักด้วย

### รายละเอียดหน้าจอ (30 จอ)

**กลุ่มเข้าระบบ (มีแล้ว — ปรับ UI ตาม DS ใหม่)**
1. Login (รหัสพนักงานหรืออีเมล + รหัสผ่าน)
2. ยืนยัน 2FA (โครงมีไว้แล้ว แม้ระบบปิด 2FA อยู่)
3. บังคับเปลี่ยนรหัสผ่านครั้งแรก (`mustChangePassword`) — **จอใหม่ จำเป็นก่อนแจกพนักงาน**

**หน้าหลัก (ทุกบทบาท)**
4. Today: สถานะวันนี้ (ยังไม่เข้า/เข้าแล้ว กี่โมง) + ปุ่มลงเวลาใหญ่ + กะวันนี้ + ใบคำขอค้าง + วันหยุดถัดไป
5. ศูนย์แจ้งเตือน (in-app inbox — ต่อ endpoint `/notifications/inbox` ที่มีแล้ว)

**ลงเวลา (พนักงาน+หัวหน้า)**
6. จอลงเวลา: แผนที่+วงรัศมี geofence, ปุ่มเข้าเช้า/เข้าบ่าย/ออกงาน ตามช่วงเวลาที่ policy เปิด, แสดงเหตุที่กดไม่ได้ (นอกรัศมี/นอกช่วง/ลงแล้ว)
7. ลงเวลานอกสถานที่ (เลือกคำขอ offsite ที่อนุมัติแล้ว)
8. ประวัติเวลาของฉันรายเดือน (มาสาย/ขาด/OT + ยอดหักแบบเดียวกับที่ HR เห็น)
9. ปฏิทินงานของฉัน (ตารางเดือน + วันหยุดบริษัท — endpoint `/ess/schedule` เสร็จแล้ว)

**คำขอ (พนักงาน+หัวหน้า)**
10. รวมคำขอของฉัน (แท็บย่อย: ลา / OT / แก้เวลา / นอกสถานที่) + สถานะไล่ขั้นอนุมัติ
11. ยื่นลา: เลือกประเภท (เห็นโควตาคงเหลือทันที) เต็มวัน/ครึ่งวัน/รายชั่วโมง + แนบรูป (กล้อง/แกลเลอรี)
12. ยื่น OT: วันที่ ช่วงเวลา ประเภทวัน + ชั่วโมงคำนวณให้
13. ยื่นแก้เวลา: เลือกวันที่มีปัญหาจากประวัติ แล้วขอเวลาใหม่
14. ยื่นนอกสถานที่
15. รายละเอียดคำขอ + ยกเลิก (ตามกติกา server: งวดล็อกแล้วยกเลิกไม่ได้ — โชว์ข้อความจาก server ตรง ๆ)

**เงินเดือน (ทุกบทบาท — flag `payslip`)**
16. รายการสลิปย้อนหลัง
17. สลิปละเอียด (รายรับ/รายหักทุกบรรทัด ตามที่ HR เปิดเผย) + ดาวน์โหลด/แชร์ PDF
18. 50 ทวิ (endpoint `/ess/salary-slips/tax-certificate` เสร็จแล้ว)

**อนุมัติ (หัวหน้า)**
19. กล่องรออนุมัติ (รวมทุกประเภท เรียงเก่าสุดก่อน) + badge
20. รายละเอียดใบคำขอ + อนุมัติ/ตีกลับ พร้อมเหตุผล + ปัด-เพื่อ-อนุมัติเร็ว
21. Dashboard ทีมวันนี้: ใครมา/สาย/ลา/ยังไม่เข้า (reuse `/manager/*`)
22. สรุปทีมรายเดือน: สาย/ขาด/OT ต่อคน

**ภาพรวม (ผู้บริหาร)**
23. บริษัทวันนี้: กำลังคน มา/ลา/ขาด แบบเรียลไทม์
24. สรุปเดือน: ค่าจ้างรวม OT รวม การลา แนวโน้ม 6 เดือน (reuse `/dashboard/*` + `/executive`)

**ฉัน (ทุกบทบาท)**
25. โปรไฟล์ + ข้อมูลงาน (อ่านอย่างเดียว — แก้ผ่าน HR)
26. เครื่องที่ล็อกอิน + ถอนเครื่องอื่น (มีแล้ว)
27. เปลี่ยนรหัสผ่าน
28. ตั้งค่าแจ้งเตือน (เปิด/ปิดรายหมวด)
29. เกี่ยวกับแอป + นโยบายความเป็นส่วนตัว (จำเป็นตอนรีวิวสโตร์)
30. ล็อกเอาต์

## 5. งานฝั่ง Backend ที่ต้องเพิ่ม (น้อย เพราะเว็บปูไว้เกือบหมด)

| งาน | ขนาด | หมายเหตุ |
|---|---|---|
| BE-1 บันทึก/ลบ `expoPushToken` ตอน register/logout เครื่อง | S | ฟิลด์มีใน schema แล้ว เติม logic ใน `mobile-devices` |
| BE-2 ยิง push ตอนเหตุการณ์สำคัญ (คำขอถูกอนุมัติ/ตีกลับ · มีใบรออนุมัติ · สลิปออก) | M | เกาะ NotificationsService เดิม + Expo Push API (มี receipt check) |
| BE-3 `GET /mobile/approvals` aggregate กล่องรออนุมัติทุกประเภทในคำขอเดียว | M | ห่อ ApprovalsService เดิม |
| BE-4 `GET /mobile/executive-summary` aggregate ภาพรวมผู้บริหาร | M | ห่อ DashboardService เดิม |
| BE-5 เพิ่ม flag `approvals`, `executive` ใน feature-flag service | S | ตามสิทธิ์ APPROVAL_ACCESS / EXECUTIVE_ACCESS |
| BE-6 สลิป PDF บนมือถือ | S | `/ess/salary-slips/:id/pdf` มีแล้ว — แค่เสิร์ฟผ่าน mobile auth ได้ (token เดียวกัน ควรผ่านอยู่แล้ว ต้องเทสยืนยัน) |
| BE-7 rate limit + audit ครบทุก endpoint ใหม่ | S | ตามแบบแผนเดิม |

ไม่ทำ: โมดูลประกาศข่าว (flag `announcements` คงเป็น false — ตัดสินใจแล้วฝั่งเว็บ)

## 6. แผนงานเป็นเฟส

> กติกาทุกเฟส: จบเฟส = typecheck + lint + unit test ผ่าน · Maestro flow ของเฟสผ่านบนเครื่องจริง
> อย่างน้อย Android 1 + iOS 1 · ไม่มี crash ใน Sentry ระหว่างทดสอบภายใน

### เฟส 2 — รื้อฐานราก + Design System (1.5 สัปดาห์)
- Design tokens ชุดเดียวกับเว็บ (sky/cyan, TH Sarabun-ish typography, ระยะ 4pt grid)
- คอมโพเนนต์แกน 12 ตัว: Button, Card, Input, Select, Sheet, Badge, ListRow, EmptyState, ErrorState, Skeleton, Toast, ConfirmDialog
- โครง navigation ตามบทบาท (แท็บ dynamic จาก flags) + จอบังคับเปลี่ยนรหัสผ่าน
- ชั้น API client ใหม่: interceptor refresh เดี่ยว (แบบเดียวกับเว็บ), error map เป็นภาษาไทย, retry policy
- ติด Sentry + source maps
- **DoD**: ล็อกอิน→เห็นแท็บตามบทบาทของ user ทดสอบ 3 แบบ · จอเดิม (punch) ยังใช้ได้บน DS ใหม่

### เฟส 3 — พนักงานครบ (3 สัปดาห์)
- ย้ายจอลงเวลาขึ้น DS ใหม่ + แผนที่ geofence + ข้อความเหตุผลที่กดไม่ได้
- ประวัติเวลา + ปฏิทิน + วันหยุด (จอ 8, 9)
- คำขอครบ 4 ประเภท: ฟอร์มยื่น + แนบรูป (บีบอัดก่อนอัปโหลด ≤1MB) + รายการ + รายละเอียด + ยกเลิก
- สลิป + 50 ทวิ + แชร์ PDF
- ศูนย์แจ้งเตือน in-app
- **DoD**: พนักงานสมมติทำครบวงจร ยื่นลา→หัวหน้าอนุมัติบนเว็บ→เห็นสถานะเปลี่ยนบนแอป→สิ้นงวดเห็นสลิป

### เฟส 4 — Push + หัวหน้า (2 สัปดาห์)
- BE-1..BE-5 + ผูก push token ตอนล็อกอิน / ถอนตอนล็อกเอาต์
- กล่องอนุมัติ + อนุมัติ/ตีกลับ + dashboard ทีม (จอ 19–22)
- Deep link: แตะแจ้งเตือน → เปิดใบคำขอนั้นทันที
- **DoD**: ยื่นลาจากมือถือเครื่อง A → push เด้งที่หัวหน้าเครื่อง B → อนุมัติจากแอป → push กลับผู้ยื่น ครบใน 1 นาที

### เฟส 5 — ผู้บริหาร + Offline (1.5 สัปดาห์)
- จอภาพรวมบริษัท (23, 24) + BE-4
- คิวลงเวลา offline: เก็บพิกัด+เวลา ณ ตอนกด ลง SQLite → ยิงซ้ำเมื่อออนไลน์ (idempotency key มีแล้วฝั่ง server) + ป้าย "รอส่ง" ชัดเจน + เพดานคิว 20 รายการ
- เปิด flag `offlinePunch` หลังผ่าน security review ภายใน (ทบทวน: ปลอมเวลาเครื่อง? → server ใช้เวลารับเป็นหลัก บันทึกเวลาเครื่องเป็นข้อมูลประกอบ)
- **DoD**: เปิด airplane mode กดลงเวลา → ปิด airplane → รายการเข้าระบบถูกต้อง ไม่ซ้ำ

### เฟส 6 — คุณภาพ/ประสิทธิภาพ (1.5 สัปดาห์)
เกณฑ์ที่ต้องผ่านเป็นตัวเลข (วัดบนเครื่องกลาง ๆ เช่น Android ราคาหมื่นต้น):
- Cold start → จอ Today ใช้ได้ **< 2.5 วิ** · warm start < 1 วิ
- แตะแท็บ → จอพร้อม < 300ms (skeleton ห้ามขาว)
- ลงเวลา: แตะ → ยืนยันบนจอ < 1.5 วิ (บนเน็ต 4G)
- Bundle: ตรวจด้วย `npx expo-atlas` — ไลบรารีเกิน 200KB ต้องมีเหตุผล
- รายการยาวทุกจอใช้ FlashList · รูปทุกจุดผ่าน expo-image + cache
- Hermes + ProGuard/R8 (Android) เปิด
- Accessibility: touch target ≥ 44pt, contrast ผ่าน WCAG AA, รองรับ font scale 1.3x ไม่แตก
- E2E Maestro 8 flow หลัก รันใน CI ทุก PR
- ทดสอบภายในจริง: พนักงาน TJC 3–5 คนใช้ 1 สัปดาห์ (TestFlight + Play Internal) เก็บ feedback

### เฟส 7 — ขึ้นสโตร์ (1–2 สัปดาห์ ขึ้นกับรอบรีวิว)
รายละเอียดเต็มในหมวด 9

**รวมประมาณ 10–12 สัปดาห์** (คนทำหลัก 1 คน + Claude) — ถ้าตัดผู้บริหาร/offline ไปเฟสหลังปล่อย เหลือ ~7 สัปดาห์ถึงสโตร์

## 7. ความปลอดภัย + PDPA

- Token เก็บใน SecureStore เท่านั้น (มีแล้ว) · ห้ามลง AsyncStorage/log
- Refresh token ผูกเครื่อง — เครื่องใหม่ = ล็อกอินใหม่ (มีแล้ว)
- เพิ่ม: ล็อกแอปด้วย biometric/PIN ก่อนเปิดหน้าสลิปเงินเดือน (expo-local-authentication)
- พิกัด GPS: ขอ **เฉพาะตอนกดลงเวลา** (foreground only) — ไม่มี background location เด็ดขาด
  (นี่คือจุดที่แอป HR โดน Apple ตีกลับบ่อยที่สุด — เราไม่ track ตำแหน่งต่อเนื่อง เขียนอธิบายใน review notes ให้ชัด)
- ไม่เก็บพิกัดสำหรับ offsite (นโยบายเดิมของระบบ)
- หน้า Privacy Policy ภาษาไทย+อังกฤษ โฮสต์บนเว็บบริษัท (สโตร์บังคับมี URL)
- ระบุใน PDPA: ข้อมูลที่เก็บ (พิกัด ณ เวลาลงเวลา, device id, push token), วัตถุประสงค์, สิทธิ์ลบ

## 8. Push Notification — สถาปัตยกรรม

```
เหตุการณ์ใน backend (อนุมัติ/ตีกลับ/สลิปออก/มีใบรออนุมัติ)
  → NotificationsService (มีแล้ว สร้าง in-app inbox อยู่แล้ว)
  → เพิ่ม MobilePushService: อ่าน expoPushToken ของ user เป้าหมาย
  → POST ไป Expo Push API (batch ได้ 100 ต่อครั้ง)
  → เก็บ ticket → ตรวจ receipt หลัง 15 นาที → token ตาย (DeviceNotRegistered) ให้ลบทิ้ง
```
- ห้ามใส่ข้อมูลเงินเดือนในข้อความ push (โผล่บนจอล็อก) — ใช้ข้อความกลาง "สลิปเงินเดือนงวดใหม่พร้อมแล้ว"
- หมวดแจ้งเตือน: คำขอของฉัน / งานรออนุมัติ / เงินเดือน — ผู้ใช้ปิดรายหมวดได้ (จอ 28)

### 9.3 Checklist ก่อน submit
**ร่วมทั้งสองสโตร์**
- [ ] ไอคอน + splash + ชื่อแอป (เสนอ: "TJC People") + screenshot ครบขนาด (ใช้เครื่องมือ gen จาก Expo)
- [ ] Privacy Policy URL ใช้งานได้
- [ ] **บัญชีเดโมสำหรับผู้รีวิว** — สร้าง user ปลอม 1 บัญชีในระบบจริง (ข้อมูลปลอมทั้งหมด) + เขียน review notes อธิบายว่าเป็นแอปพนักงานองค์กร, GPS ใช้เฉพาะตอนลงเวลา

**Apple เฉพาะ**

- [ ] `NSLocationWhenInUseUsageDescription` ภาษาไทย+อังกฤษ อธิบายว่าใช้ยืนยันการลงเวลา ณ สถานที่ทำงานเท่านั้น
- [ ] ไม่มีปุ่มสมัครสมาชิกในแอป → ไม่ติดเงื่อนไข account deletion (บัญชีบริหารโดยองค์กร — เขียนใน notes)
- [ ] Sign in with Apple: ไม่บังคับ เพราะไม่มี third-party login

**Google เฉพาะ**
- [ ] Data Safety form (ให้ตรงกับ Privacy Labels ของ Apple)
- [ ] target API level ล่าสุดตามข้อกำหนดปีนั้น (EAS จัดการ)
- [ ] Play Internal testing → Closed testing (พนักงานจริง) → Production

### 9.4 Build & Release ด้วย EAS
```
eas.json profiles:
  development  — dev client + สลับ API ไป dev server ได้ในแอป
  preview      — internal distribution (APK/TestFlight) ชี้ staging
  production   — store build ชี้ API จริง (HTTPS + โดเมนจริงเท่านั้น)
```
- Versioning: `1.0.0` + autoIncrement build number
- **EAS Update (OTA)**: ใช้แก้ bug ระดับ JS ระหว่างรอบรีวิว — ห้ามเปลี่ยนพฤติกรรมหลักผ่าน OTA (ผิดนโยบายสโตร์) · channel ผูกกับ profile
- CI: ทุก PR รัน typecheck+test+Maestro · merge เข้า main → EAS build preview อัตโนมัติ

### 9.5 เงื่อนไขฝั่ง server ก่อนปล่อย production build
- API ต้องเป็น **HTTPS โดเมนจริง** (iOS ATS ไม่ยอม http) — งานติดตั้ง server ของโปรเจกต์หลัก
- `.env` โปรดักชัน + rate limit + backup ตามแผนส่งมอบเว็บ

## 10. โครงสร้างโค้ดใหม่

```
src/
  app/                      # expo-router
    (auth)/                 # login, 2fa, change-password
    (app)/
      (tabs)/               # แท็บ dynamic ตามบทบาท
      requests/[type]/new   # ฟอร์มยื่น
      requests/[id]         # รายละเอียด
      approvals/[id]
      payslips/[id]
  design/                   # tokens + คอมโพเนนต์ 12 ตัว (ห้าม import สีตรงนอกโฟลเดอร์นี้)
  features/
    auth/ attendance/ requests/ payslip/ approvals/ team/ executive/ notifications/ profile/
    # ต่อ feature: api.ts (typed) · hooks.ts (React Query) · components/ · screens อยู่ใน app/
  lib/
    api/                    # client + interceptor + error map
    database/               # SQLite: คิว punch + cache persist
    push/
    monitoring/             # Sentry
  config/
```

กติกาโค้ด: ทุก endpoint มี type ตรงกับ backend (สร้าง type ด้วยมือใน `features/*/api.ts` อ้าง DTO backend) · ห้าม `any` · ข้อความ error ทุกจุดเป็นภาษาไทยที่ผู้ใช้อ่านรู้เรื่อง ไม่โชว์ technical message
